01Getting started

git clone https://github.com/hardrave/NIGHTRUN.git
cd NIGHTRUN
./install.sh

The installer picks a target (x86_64 USB or Raspberry Pi 5 SD), a model, builds a bootable image and flashes it with verification — the full walkthrough lives on the Install page. Boot the media and you land in the chat.

Using the chat

InputEffect
Entersends the prompt — it appears in the transcript immediately, the input locks with >> generating — press ESC to stop, and a blinking block beside the model label shows it is preparing the first token
ESCstops a running generation cleanly
← / →, Backspace, Deleteedit the prompt at the caret — fix a typo mid-sentence without retyping
Up / Down, PgUp / PgDnscroll conversation history; a banner shows how far back you are
/clearfresh conversation: transcript and context reset, model stays resident — instant
/byereal power-off via UEFI runtime services

The status bar tracks reality: core count (8c), memory in use, context fill (ctx 91/4096), prompt throughput (pp), first-token latency (ftl) and live generation speed. When the context window would overflow, the conversation resets itself and says so.

02Command reference

Installer

./install.sh                          # the guided flow (see section 5)
NIGHTRUN_INSTALL_DEBUG=1 ./install.sh # same, with full tracing into the log dir
scripts/installer/tests/run.sh        # installer test suite - never touches a real disk
sudo scripts/installer/tests/loopback.sh  # flash+verify against a loop device

Building and images (xtask)

cargo xtask build                     # BOOTX64.EFI (custom hard-float UEFI target, nightly)
cargo xtask build --arch aarch64      # BOOTAA64.EFI (stock target, stable toolchain)
cargo xtask image --model m.nrm       # x86_64 GPT/ESP image -> nightrun.img
cargo xtask pi-image --model m.nrm    # Pi 5 SD image with UEFI firmware -> nightrun-pi5.img
cargo xtask bench                     # scripted benchmark boot -> docs/benchmarks.md

Running in QEMU

cargo xtask run --img --model models/granite-4.1-3b-q4km.nrm --mem 5G --smp 8 --window

Model conversion

cargo run --release -p nrconvert -- --inspect model.gguf   # architecture + per-tensor dtypes
cargo run --release -p nrconvert -- model.gguf model.nrm   # convert; validates its own output

cargo run --release -p nrhost -- models/model.nrm --prompt "..." --threads 8

Tests

cargo test                                              # host suite: kernels, tokenizer, parity, prefill, format
cargo test -p nr-tensor --target aarch64-unknown-linux-musl  # NEON kernels under qemu-user

Three architecture families are implemented — Llama 3.2, Qwen3, and Granite 4.1 dense transformers (hybrid SSM/MoE Granite is rejected at conversion; see the per-family notes). Supported tensor quantizations are Q8_0, Q4_K, Q6_K and F32 — any GGUF build whose tensors use these converts with each tensor's exact dtype preserved: Q8_0, Q4_K_M, Q4_K_S and Q6_K artifacts all qualify. "Q4_K_M" is a per-tensor policy, not one format: such a file mixes Q4_K attention/FFN weights with Q6_K embeddings and F32 norms, and NightRun keeps that mix.

The catalog manifest

config/models.manifest drives the installer's menu — one block per model with a pinned Hugging Face revision (a commit, so moved branches can't change downloads), the exact filename, SHA-256, license label, minimum RAM, supported targets and sizes. The format is plain model.<id>.<key> = value lines, parsed as data (never executed).

Adding a model

# 1. pin the revision + hash without downloading:
curl -sI https://huggingface.co/REPO/resolve/main/FILE.gguf | grep -iE "x-repo-commit|x-linked-etag"
# 2. append a model block to config/models.manifest with those pins
# 3. validate:
scripts/installer/tests/run.sh

A manifest entry only lists a model; runtime compatibility is still gated by nrconvert's inspection, and genuinely new architecture families need engine work plus reference validation — not just a manifest line.

04The .nrm format

NightRun's runtime format (version 3), designed so that loading is the last copy ever made:

Layout

SectionContents
Header (192 B)magic + version + architecture id; dimensions (layers, heads, KV heads, hidden/attention/FFN widths, vocabulary, max context); RoPE parameters (θ, scaling, adjacent vs NEOX style); feature flags (tied embeddings, …); four scalar multipliers (embedding, attention, residual, logit) — Granite's muP scaling lives here, neutral values elsewhere, applied branch-free
Tokenizer blobvocabulary, merges, special tokens, pretokenizer id, chat-template id — everything the runtime needs to talk to the model correctly
Tensor tableper tensor: kind, dtype (F32 / Q8_0 / Q4_K / Q6_K), shape, offset — the source artifact's per-tensor quantization preserved exactly
Data64-byte-aligned tensor bytes, used in place after load (zero-copy views)
Integritytwo CRC-32 section checksums (metadata, data) — verified while the file streams into RAM at boot; no post-load pass

Conversion diagnostics

Failures are named, not mysterious: unsupported architecture families ("hybrid granite: rejected"), missing tensors, unknown dtypes, or tokenizer inconsistencies fail at convert time with a reason. The converter then re-parses its own output, re-checksums both sections, and smoke-tests the tokenizer — a corrupt .nrm should be impossible to produce silently.

05Installer / Image Forge reference

Full text: docs/installer.md. The rules that matter:

Device safety

  • Only whole disks on USB/SD transports are ever listed — partitions never, loop/zram/optical/RAID/device-mapper never.
  • Disks backing /, /boot, /home or active swap are excluded by proof (mount-table resolution), not by heuristics.
  • Internal SATA/NVMe disks are unsafe by default even when they claim to be removable — enclosures lie in both directions, so transport is the trusted signal.
  • Every device carries an identity fingerprint (path + size + model + serial + major:minor), re-verified before unmounting and again immediately before the first byte is written — a re-enumerated /dev/sdX aborts instead of hitting the wrong disk.
  • There is no default device and no auto-pick; an empty list is a normal state with Rescan.

The confirmation

Two stages, both defaulting to no: a menu confirmation, then typing FLASH /dev/sdX exactly — current device path included; y, case variants, partition paths and stale paths are all rejected. One deliberate sentence instead of a reflex.

Verification

After writing (4 MiB direct-I/O blocks, synced), the installer reads back exactly the image-sized region and compares SHA-256 digests with the source image. Verification is the default; skipping requires a separate warned confirmation. A mismatch reports the media as unreliable and never calls it bootable.

Downloads and secrets

Model downloads resume (curl -C -), verify size + SHA-256 + GGUF structure, and install atomically. For gated repositories, a token is read from HF_TOKEN or a hidden prompt; it is never echoed, never logged, never persisted, and never appears on a command line. NIGHTRUN_INSTALL_DEBUG=1 traces everything except the token-handling paths, which disable tracing locally.

06Tokenizer and template reference

A model that loads perfectly but tokenizes almost-correctly produces subtly wrong output — the least debuggable failure mode there is. NightRun pins tokenization as hard as it pins kernels:

  • Byte-level BPE with each family's own pretokenizer regex (Llama-3 and Qwen differ; Granite uses its dbrx-style pretokenizer).
  • Fixtures from the source of truth: scripts/gen_tokenizer_fixtures.py generates test cases from the official Hugging Face tokenizers with split_special_tokens=True — text a user types must never encode into control tokens, even if it spells one.
  • Template parity: chat templates are compared token-for-token against apply_chat_template output. Family differences that these tests guard: Qwen3 has no BOS and ChatML-style headers; Granite has no dedicated BOS (EOS doubles for it); Llama-3 uses its instruct header structure.
  • Round-trips: decode(encode(x)) identity and special-token handling are fixture-tested per family.

Debug tip: when output "feels wrong", run the same prompt through nrhost --raw (no template) and with the template — if only the templated path misbehaves, the conversation framing is the suspect, not the model.

07Developing and testing

The development loop

cargo test                       # engine correctness on the host - seconds
cargo run --release -p nrhost -- models/model.nrm --prompt "..."   # same engine, host speed
cargo xtask run --img --window   # full boot in QEMU when platform behavior matters

The engine crates are dual-target: no_std for the EFI build, std for the host. Debug inference on the host first — QEMU is for platform work (boot, video, input, SMP), and its serial log lands in target/serial.log.

What the test suite pins

  • Kernel equality: AVX2 and NEON dots against scalar references — adversarial values, saturated blocks; the NEON kernels are bit-identical to scalar by construction and asserted with ==.
  • Prefill bit-identity: batched prompt processing produces the same logits and the same KV cache as token-at-a-time, verified against real models.
  • Reference parity: greedy generations match llama.cpp token-for-token for all families. The rule is absolute: break parity and the code is wrong, not the fixture. One documented nuance — Granite's ÷10 logit scaling compresses top-2 gaps, so near-ties can legitimately flip between numerically-equivalent implementations; nrhost --debug-gap measures the gap so real bugs and coin-flips are distinguishable.
  • Format integrity: the streaming verifier is tested against deliberately corrupted files, byte-flip by byte-flip.

08Benchmark methodology

Four numbers answer four different questions:

  • Prompt throughput (pp) — batched prefill speed; dominates time-to-first-token for long prompts;
  • Decode throughput (tg) — interactive generation; memory-bandwidth-bound;
  • First-token latency (ftl) — what pressing Enter feels like;
  • Boot-to-chat — power-on to usable, model load included.

Context length matters

Decode reads the entire KV cache every token, so generation slows as the context fills. Measured on the host (8 threads): Granite decodes ~13 tok/s early in a conversation and averages 11.6 tok/s across a 384-token generation — still fluid, honestly slower, and the effect continues to grow toward the 4096-token window. Short-context headline numbers are the best case, which is why this table labels them.

Fair comparisons

llama.cpp comparisons are made greedy, same GGUF, same machine: on that basis NightRun's decode is comparable and its batched prefill lands within 1.15–1.4× of llama.cpp's. NightRun makes no claim of being globally faster — the point of the project is where it runs, not a speed crown. QEMU numbers vary ±20% with host load; single benchmark numbers without conditions are noise.

10Limitations and non-goals

  • Not a general-purpose OS — no desktop, no applications, no networking. A single-purpose chat appliance, on purpose.
  • Three architecture families, individually validated. No arbitrary GGUF compatibility; hybrid Granite variants are out of scope by design.
  • RAM-bounded — the entire model is always resident; if it doesn't fit, it doesn't run.
  • CPU only — there is no GPU path; performance ceilings are memory-bandwidth ceilings.
  • UEFI required, Secure Boot off — images are unsigned.
  • UEFI-resident by design — Boot Services stay up; no post-ExitBootServices() claim is made (the honest why: Architecture §3).
  • Pi 5 firmware is community-maintained — built from a pinned, diff-reviewed source; the full risk discussion lives in docs/rpi5-uefi.md.
  • Young project — tested and working, with sharp edges at hardware-compatibility margins.

11Roadmap

Working notes, honestly labeled — not commitments.

  • In validation: Raspberry Pi 5 benchmarks with the sdot NEON kernels; sustained-load thermal runs with the fan driver.
  • Planned validation: C1-stepping Pi 5 boards (tooling supports them; untested on maintainers' hardware).
  • Exploration: NVMe model storage on the Pi 5 for faster loads; a post-ExitBootServices() research backend.
