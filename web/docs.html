//Getting started

git clone https://github.com/hardrave/NIGHTRUN.git
cd NIGHTRUN
./install.sh

The installer chooses a target (x86_64 USB / Pi 5 SD), a model, builds the image and flashes it safely — full walkthrough on the Install page. In the chat: type and press Enter; ESC stops a generation; Up/Down scroll history; arrow keys edit the prompt at the caret; /clear starts a fresh conversation with the model still resident; /bye is a real UEFI power-off.

//Model support and manifests

Three families are supported and continuously tested: Llama 3.2, Qwen3, and Granite 4.1 (dense transformer only) — see the per-family architecture notes. Compatibility is decided by inspected metadata, never by filename.

The installer's catalog lives in config/models.manifest: per model, a pinned Hugging Face revision, exact filename, SHA-256, license label, minimum RAM, supported targets and sizes. To add a model, append a block with a new id, pin its revision and hash (the repo's HTTP headers expose the LFS SHA-256 without downloading), and run the installer test suite — it validates required fields. Runtime compatibility is still gated by nrconvert regardless of what a manifest claims.

//The .nrm format

NightRun's runtime format (version 3), designed for zero-copy load-and-run:

  • Header — magic, version, architecture id; dimensions (layers, heads, KV heads, hidden/attention/FFN widths, vocabulary, context); RoPE parameters (θ, scaling, style); feature flags (e.g. tied embeddings); four scalar multipliers (embedding, attention, residual, logit) with neutral values for families that don't use them — applied branch-free at runtime;
  • Tokenizer blob — vocabulary, merges, special tokens, pretokenizer id, chat-template id;
  • Tensor table — kind, dtype (F32 / Q8_0 / Q4_K / Q6_K), shape, offset per tensor: the per-tensor quantization of the source artifact is preserved exactly;
  • Data section — 64-byte-aligned tensor bytes, viewed in place after load;
  • Two section CRCs (metadata, data) — verified while the file streams into RAM at boot; no post-load pass.

Conversion failures are diagnostics, not mysteries: unsupported architectures (hybrid Granite, MoE), missing tensors, or unknown dtypes are named at convert time. The converter also re-parses and re-checksums its own output and smoke-tests the tokenizer.

//Installer / Image Forge reference

Safety rules the installer enforces, and why (full text: docs/installer.md):

  • Only whole disks on USB/SD transports are ever listed; disks backing /, /boot, /home or active swap are excluded by proof, not heuristics; internal disks are unsafe by default even if they claim to be removable.
  • No default device, no auto-pick, partitions are never flash targets.
  • Each device gets an identity fingerprint (path + size + model + serial + major:minor), re-verified before unmounting and again immediately before writing — a re-enumerated device path aborts instead of hitting the wrong disk.
  • Destruction requires two stages, both defaulting to no: a menu confirmation, then typing FLASH /dev/sdX exactly. One deliberate sentence, not a y reflex.
  • Writes are readback-verified by SHA-256 over exactly the image-sized region (default on; skippable only past an explicit warning).
  • Downloads: pinned revision + SHA-256 + GGUF structure check, resumable, atomically installed; tokens (for gated repos) come from HF_TOKEN or a hidden prompt and are never echoed, logged or persisted.
  • sudo is scoped to the four commands that need it (umount fallback, dd write, dd readback, partprobe), each shown before running.

//Tokenizer and template reference

Each family carries its own pretokenizer regex, special tokens and chat template. Fixtures are generated from the official Hugging Face tokenizers (scripts/gen_tokenizer_fixtures.py) with split_special_tokens=True — a user typing the literal text of a control token must never produce that control token. Chat templates are pinned token-for-token against apply_chat_template. Family gotchas that these tests guard: Qwen3 has no BOS and ChatML-style headers; Granite falls back to EOS as its BOS; Llama-3 uses its instruct header structure. When a model "loads fine but acts weird", tokenization is the first suspect — nrhost --raw bypasses the template for isolation.

//Benchmark methodology

Four numbers matter, and they answer different questions:

  • Prompt throughput (pp) — batched prefill tok/s; dominates time-to-first-token for long prompts;
  • Decode throughput (tg) — interactive generation tok/s; memory-bandwidth-bound;
  • First-token latency (ftl) — what a user actually feels after pressing Enter;
  • Boot-to-chat — power-on to usable, including the model load.
Modelpptgboot→chatConditions
Llama 3.2 1B Q8_052 tok/s~20 tok/s5.6 sQEMU/KVM q35, 8 cores, AVX2 host, 4 GB
Granite 4.1 3B Q4_K_M25 tok/s~13 tok/s9.5 sQEMU/KVM q35, 8 cores, AVX2 host, 5 GB
Qwen3 4B Q4_K_M21 tok/s~10 tok/s11.5 sQEMU/KVM q35, 8 cores, AVX2 host, 6 GB
Granite 4.1 3B Q4_K_M6.2 tok/s3.0 tok/s~30 s (SD load)Raspberry Pi 5 (8 GB, D0), 4 cores, NEON, pre-sdot kernels

Conditions matter more than single numbers: thread count, context length, prompt length, generated-token count and host memory pressure all move results (QEMU numbers vary ±20% on a busy host). Comparisons with llama.cpp are made greedy, same GGUF, same machine — on that basis NightRun's decode is comparable and its prefill is within 1.15–1.4× after batching; NightRun makes no claim of being globally faster. Correctness comparisons additionally account for Granite's compressed logit gaps (its ÷10 logit scaling makes greedy near-ties flip between numerically-equivalent implementations — measured with nrhost --debug-gap).

//Limitations and non-goals

  • Not a general-purpose OS: no desktop, no apps, no networking — a chat appliance by design.
  • Three model families, validated individually; no arbitrary GGUF compatibility, and hybrid Granite variants are out of scope.
  • Models are bounded by RAM — everything is resident, always.
  • CPU inference only; there is no GPU path.
  • UEFI is required; Secure Boot must be disabled (images are unsigned).
  • The Pi 5 depends on community-maintained UEFI firmware (built from a pinned, reviewed source — see docs/rpi5-uefi.md for the full honesty file).
  • The runtime stays on UEFI Boot Services deliberately; no post-ExitBootServices() claim is made.
  • Status: a working, tested system — and still a young project. Expect sharp edges at the hardware-compatibility margins.

//Roadmap

Working notes, not promises. Labeled by nature:

  • In validation: Pi 5 benchmarks with the new sdot kernels; sustained-load thermal runs now that the fan is driven.
  • Planned validation: C1-stepping Pi 5 boards (currently supported-but-untested by the maintainers' own hardware).
  • Exploration: NVMe model storage on the Pi 5 (faster loads); a post-ExitBootServices() research backend.

//Source and contributing

Everything lives at github.com/hardrave/NIGHTRUN: runtime crates · tools · installer · architecture notes · benchmark logs · issues. The test suite is the contribution contract: kernel changes must keep the llama.cpp parity pins green — if parity breaks, the code is wrong, not the fixture.
