Install NightRun

Boot a local LLM runtime from a USB drive or a Raspberry Pi 5 microSD card.

Flashing boot media permanently erases the selected USB drive or microSD card. The guided installer requires an exact typed confirmation naming the device; when flashing manually, always double-check the target with lsblk first.

//Guided installation (recommended)

The interactive installer handles the whole journey:

git clone https://github.com/hardrave/NIGHTRUN.git
cd NIGHTRUN
./install.sh

It walks you through, in order:

  • choosing x86_64 UEFI or Raspberry Pi 5 (genuinely different images);
  • choosing a model from a target-filtered catalog, or bringing your own GGUF;
  • downloading the exact pinned artifact with SHA-256 verification, or inspecting your local file's real metadata;
  • converting to NightRun's format and assembling the correct target image;
  • detecting removable USB/SD media — system disks are never listed;
  • unmounting the target only after your explicit approval;
  • a two-stage destructive confirmation (the second stage is typing FLASH /dev/sdX exactly);
  • flashing the whole device with progress, then verifying by reading it back;
  • printing target-specific boot instructions.

Prefer to inspect before running? Read install.sh on GitHub and the installer documentation — the clone-first path above is always the recommended one, and there is deliberately no pipe-to-shell-only flow.

//x86_64 UEFI — guided

Host requirements
Linux with Bash ≥ 4, Rust via rustup (stable + nightly with rust-src), ~10 GB free disk for model + image work
Boot media
USB drive, 4 GB or larger
Target machine
x86_64 with UEFI firmware, USB boot enabled, Secure Boot off; AVX2 CPU strongly recommended (a scalar fallback exists but is slow)
Target RAM
Llama 1B: 4 GB · Granite 3B: 6 GB · Qwen3 4B: 8 GB

Run ./install.sh, choose [1] x86_64 UEFI, pick a model, and follow the flow. When it finishes: plug the USB drive into the target machine, open the firmware boot menu (typically F12, F10 or Esc at power-on), select the NightRun drive, and boot. The splash appears, the model loads with a progress bar, and the chat is ready in seconds.

//Raspberry Pi 5 — guided

Board
Raspberry Pi 5 (D0 and C1 revisions supported; D0 hardware-verified)
Boot media
microSD card, 4 GB or larger (A1/A2-rated cards load the model faster)
EEPROM
2025-06-09 or newer — older EEPROMs break UEFI graphics on D0 boards; update from Raspberry Pi OS with sudo rpi-eeprom-update -a before first boot
Peripherals
HDMI display (use the port next to USB-C), USB keyboard, 5 V/3 A+ power, active cooling recommended
Models
Granite 3B (default) and Llama 1B on any board; Qwen3 4B needs an 8 GB board

The Pi image embeds UEFI firmware compiled from a pinned, reviewed source tree — if it isn't built yet, the installer offers to run scripts/build-rpi5-firmware.sh for you (needs gcc-aarch64-linux-gnu acpica-tools uuid-dev). Then choose [2] Raspberry Pi 5 and follow the same flow. First boot shows a QR screen, then the Raspberry Pi logo, then NightRun's splash. Details and bring-up notes: docs/rpi5-uefi.md.

//Manual installation — x86_64

Every step the installer automates, by hand.

1 · Toolchain and build

rustup toolchain install nightly --component rust-src
cargo xtask build          # builds BOOTX64.EFI (custom hard-float UEFI target)
cargo test                 # host test suite: kernels, tokenizer, parity

2 · Get and convert a model

mkdir -p models
curl -L -o models/granite-4.1-3b-Q4_K_M.gguf \
  https://huggingface.co/ibm-granite/granite-4.1-3b-GGUF/resolve/main/granite-4.1-3b-Q4_K_M.gguf
cargo run --release -p nrconvert -- \
  models/granite-4.1-3b-Q4_K_M.gguf models/granite-4.1-3b-q4km.nrm

nrconvert --inspect file.gguf shows an artifact's architecture and per-tensor dtypes before you commit to converting it. The converter validates its own output: it re-parses the file, re-checksums it, and smoke-tests the tokenizer.

3 · Assemble the image

cargo xtask image --model models/granite-4.1-3b-q4km.nrm
# optional dry run before flashing:
cargo xtask run --img --model models/granite-4.1-3b-q4km.nrm --mem 5G --window

4 · Identify the USB drive and flash

lsblk -o NAME,SIZE,TRAN,MODEL,MOUNTPOINTS
sudo dd if=nightrun.img of=/dev/REPLACE_WITH_USB_DISK bs=4M status=progress conv=fsync
dd writes to the whole disk and permanently erases it. The target must be the disk device (like /dev/sdb), never a partition (/dev/sdb1 is wrong). Check lsblk output twice — size, transport and model name should all match your stick.

5 · Boot

Firmware boot menu (F12/F10/Esc) → select the USB drive in UEFI mode, Secure Boot disabled. A serial console on COM1 (115200) carries debug logs if you want them.

//Manual installation — Raspberry Pi 5

1 · Build the Pi UEFI firmware from pinned source

sudo apt install gcc-aarch64-linux-gnu acpica-tools uuid-dev
rustup target add aarch64-unknown-uefi
scripts/build-rpi5-firmware.sh     # TF-A + EDK2 at a reviewed pin; prints SHA-256s

2 · Convert a model (same as x86) and assemble the SD image

cargo xtask pi-image --model models/granite-4.1-3b-q4km.nrm
# produces nightrun-pi5.img: MBR + FAT32 with firmware, DTBs, BOOTAA64.EFI, model

3 · Flash the microSD card

lsblk -o NAME,SIZE,TRAN,MODEL,MOUNTPOINTS
sudo dd if=nightrun-pi5.img of=/dev/REPLACE_WITH_SD_CARD bs=4M status=progress conv=fsync

4 · First boot

  • Make sure the board's EEPROM is 2025-06-09 or newer (see the guided section above).
  • Insert the card, connect HDMI (port next to USB-C) and a USB keyboard, power on.
  • Expected sequence: QR screen → Raspberry Pi logo with progress bar → NightRun splash → model loading → chat.

//Model sources

Two acquisition paths, both ending in the same validation:

  • Verified download — the installer's catalog pins each model to an exact Hugging Face revision and SHA-256; downloads resume, verify, and are checked for real GGUF structure before use. None of the catalog models are gated; if you add one that is, the installer explains the official license-acceptance flow and takes a token securely (never echoed, never stored).
  • Local GGUF — your file is inspected for its actual architecture and tensor dtypes; a filename saying "Q4_K_M" proves nothing and is not trusted. Supported families: Llama, Qwen3, and dense Granite. Hybrid Granite, SSM and MoE artifacts are rejected with an explanation.

Model weights are licensed by their publishers (Llama Community License; Apache-2.0 for Qwen and Granite builds used here) — respecting those licenses is your responsibility. Once media is prepared, the runtime itself is fully offline.

//Flashing and verification

The guided installer writes the whole device in 4 MiB direct-I/O blocks, flushes, and then reads back exactly the image-sized region and compares SHA-256 digests with the source image. A mismatch is reported as unreliable media — the drive is never called bootable on hope. Manual flashers can approximate this with: 

IMG_BYTES=$(stat -c %s nightrun.img)
sudo dd if=/dev/REPLACE_WITH_USB_DISK bs=4M iflag=count_bytes count=$IMG_BYTES status=none | sha256sum
sha256sum nightrun.img   # the two digests must match

//Troubleshooting

SymptomWhat to do
No removable drive detectedOnly USB/SD devices large enough for the image are listed — system disks never are. Insert media and choose Rescan.
Drive cannot be unmountedSomething is using it: close file managers and terminals inside it. The installer names the blocking partition.
Not enough disk spaceModel download + conversion + image needs up to ~8 GB free in the repo; clear space or use the smaller Llama model.
Model does not fit target RAMPick per the table: Llama 4 GB, Granite 6 GB, Qwen 8 GB. The boot screen reports an arena failure otherwise.
GGUF incompatibleRun nrconvert --inspect — only Llama/Qwen3/dense-Granite families are supported; hybrids are rejected by design.
Conversion or image build failsFull logs are kept in build/nightrun-installer-logs/<timestamp>/; the failing stage is named.
Verification mismatchUsually worn flash or a flaky reader: re-flash; if it repeats, use different media. The drive is not trustworthy for boot.
USB doesn't appear in the boot menuEnable UEFI USB boot, disable Secure Boot, try another port; some firmwares list it under "UEFI: <stick name>".
Pi shows nothing on screenUpdate the EEPROM (≥ 2025-06-09), use the HDMI port next to USB-C, and see docs/rpi5-uefi.md — the bootloader's Esc log diagnoses the stage.
Keyboard not detectedUse a plain wired keyboard; on the Pi prefer the black USB 2.0 ports. Wireless dongles sometimes never enumerate in firmware.
Model loading is slowLoad speed is media-bound: use USB 3 sticks / A1-A2 SD cards. ~1–2 GB loads in tens of seconds on decent media.
