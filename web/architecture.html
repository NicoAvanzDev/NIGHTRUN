NightRun Architecture

A purpose-built local LLM runtime that boots from USB and runs without a conventional operating system: UEFI-resident by deliberate design, not "pure bare metal" by slogan.

01Overview

  1. UEFI firmware
  2. NightRun Rust entry & runtime single no_std EFI application
  3. Platform layer framebuffer (GOP) · USB keyboard · disk · multicore startup
  4. Model loader .nrm parsing + inline CRC verification, then storage sealed
  5. Model fully in RAM zero-copy quantized tensor views
  6. Tokenizer · chat template · KV cache preallocated arenas
  7. Batched prompt prefill up to 64 tokens per pass
  8. Single-token decode quantized matvec across all cores
  9. Framebuffer chat UI

Everything below the firmware line is NightRun's own code: the graphics stack, the font renderer, the tokenizer, the inference kernels, the scheduler-free worker pool, and the chat itself. The engine crates are platform-independent and run identically on a Linux host, which is how most of the correctness testing happens.

02What NightRun is, and is not

There is no operating system underneath the chat you see. Concretely, there is:

  • no Linux kernel or userspace, no desktop environment, no browser;
  • no background services, no package manager, no shell;
  • no host process "running the model": the runtime is the machine's software;
  • no network stack, and therefore no cloud dependency of any kind.

Equally plainly: NightRun remains a UEFI Boot Services application for its entire session. It never calls ExitBootServices(). That is an intentional compatibility decision (UEFI is used as firmware platform support, not as an operating system) and it is fundamentally different from booting Linux to run a program. But it also means NightRun does not claim post-ExitBootServices() purity. The next section explains the tradeoff.

03Why UEFI-resident?

Staying on Boot Services buys four hard things at zero driver-development cost:

  • Graphics: the GOP framebuffer works on any UEFI machine, in whatever mode the firmware negotiated with the display.
  • Keyboards: USB HID via the firmware's own USB stack; writing a bare-metal xHCI + HID stack is a project in itself.
  • Storage: the FAT filesystem driver reads the model off the boot medium; NightRun only needs it until the model is resident.
  • Multicore: the UEFI MP services protocol starts every core into NightRun's worker pool.

The accepted tradeoffs: firmware code stays mapped, timers and event infrastructure remain the firmware's, and true ownership of the MMU/interrupts is out of scope. One strict internal rule keeps the runtime disciplined: worker cores never call firmware services; they run pure compute on atomics. And after the model loads, the storage path is sealed at the runtime level: any later disk access is a hard fault, by design. A post-ExitBootServices() backend would be an interesting research direction; it is not implemented and is not claimed.

04Boot sequence

  1. Firmware loads BOOTX64.EFI / BOOTAA64.EFI
  2. SIMD state enabled x86: CR4/XCR0 dance for AVX · ARM: FP/SIMD un-trapped at EL2
  3. Graphics + keyboard up panic handler gets its own framebuffer screen
  4. All cores started MP services, then the lock-free worker pool
  5. RAM discovered conventional-memory scan
  6. Model streams into RAM 16 MB chunks; CRC-32 computed inline, no second pass
  7. Storage sealed later disk reads are a hard fault
  8. Tokenizer initialized byte-level BPE + the model family's chat template
  9. Arenas allocated KV cache + all inference scratch, sized up front
  10. Chat ready 5.6 s after splash for Llama 1B in QEMU; ~9.5 s for Granite

The checksum design is worth a note: the naive approach verifies the model after loading, costing a full second pass over gigabytes. NightRun hashes each chunk as it streams (slicing-by-8 CRC-32, fast enough to hide inside disk I/O), so verification is effectively free and corrupt media fails mid-load with a clear message.

05Model residency and memory design

Memory is laid out once, at boot, and never reorganized:

RegionContentsNotes
Model blobweights, tokenizer payload, metadatatensors are zero-copy views into this blob; quantized data is used in place
KV cachef16 keys/values, all layers × contextsized for the full 4096-token context up front
Prefill workspacebatched activations (up to 64 rows)~10–20 MB depending on model
Decode scratchactivations, logits, quantization buffersreused every token
UI bufferssurface + framebufferthe chat renderer

A single arena covers the KV cache and all scratch, sized by one function (InferCtx::required_bytes) so the runtime either has everything it will ever need or fails at boot with a clear message. The generation loop performs zero heap allocations. After residency, the model is never read from disk again: predictable latency is a design goal, not an accident. /clear resets the conversation and the KV position while the weights stay resident; a fresh conversation costs nothing.

RAM requirements follow model size: Llama 1B ≈ 4 GB machines, Granite 3B ≈ 6 GB, Qwen3 4B ≈ 8 GB (model + KV cache + firmware overhead).

06The inference pipeline

Prompt prefill

Many tokens at once. Batched, GEMM-like work: each weight row is loaded once and reused across the whole batch. Determines time to first token.

Decode

One token at a time. Matrix-vector work bounded by memory bandwidth; every weight is read once per token. Determines interactive speed.

Prefill processes prompts in batches of up to 64 tokens per pass; arbitrary prompt lengths are chunked (a 129-token prompt runs as 64 + 64 + 1). The batched kernels use 4-wide register tiles that share weight loads and dequantization bookkeeping across tokens. The crucial property, enforced by tests: batched prefill is bit-identical to sequential decode (same kernels, same operation order), so it cannot change model behavior, only speed. On 8 cores, batching took Llama prompt processing from 21 to 56 tok/s, within striking distance of llama.cpp on the same machine.

07Quantization and CPU kernels

Local CPU inference lives and dies by memory bandwidth, which is why NightRun runs directly on quantized weights. Supported tensor formats are PQ2_0 (128 ternary weights plus an f16 scale), Q8_0 (32-weight blocks), Q4_K and Q6_K (256-weight super-blocks with 6-bit scale metadata); "Q4_K_M" is a per-tensor dtype policy, not a single format: a Q4_K_M artifact mixes Q4_K, Q6_K and F32 tensors, and NightRun preserves each tensor's exact quantization through conversion.

  • x86_64: AVX2 + FMA integer dot products (maddubs/madd), F16C for the f16 KV cache. A custom hard-float UEFI target, because the standard one is soft-float, which breaks vector intrinsics.
  • AArch64: NEON kernels with a runtime-dispatched sdot (FEAT_DotProd) fast path: one instruction per 16 int8 products on the Pi 5's Cortex-A76.
  • Scalar reference kernels exist for every format and double as the correctness oracle: the NEON kernels are constructed to be bit-identical to scalar (exact integer dots + replicated f32 ordering), and tests assert equality with ==, not tolerances.
  • Weight matrices are dtype-tagged and dispatched once per matvec, never inside row loops. Activations are quantized once per layer into the matching format (Q8_0 or Q8_K).

Nothing is ever materialized as F32 weights; a 4 GB machine simply couldn't hold it, and the bandwidth cost would erase the point of quantization.

08Model format and conversion

  1. GGUF artifact from Hugging Face or local
  2. Inspection architecture, tensor dtypes, tokenizer: metadata, not filenames
  3. Validation unsupported families rejected with a reason
  4. .nrm conversion nrconvert; output is re-parsed and re-checksummed
  5. Target image x86_64 GPT/ESP image or Pi 5 SD image
  6. Full RAM load at boot

.nrm is NightRun's runtime format: a fixed header with model dimensions, RoPE parameters, feature flags and four per-model scalar multipliers (Granite's muP scaling needs them); a tensor table with per-tensor dtype descriptors; the tokenizer blob (vocabulary, merges, special tokens, pretokenizer id, chat template id); and 64-byte-aligned tensor data. Two section checksums (metadata and data) let the loader verify integrity while streaming. The design goal is zero-copy: the loaded blob is the runtime's tensor memory. Unsupported artifacts (hybrid Granite, MoE, unknown architectures) fail conversion with a diagnostic instead of failing mysteriously at boot.

09Supported model families

Llama 3.2

  • Conventional decoder: RMSNorm, GQA attention, SwiGLU MLP
  • Adjacent-pair RoPE with Llama-3's long-context frequency scaling
  • Llama-3 instruct template and pretokenizer

Qwen3

  • NEOX-style RoPE (half-split pairs; silently wrong output if you assume Llama's layout; caught here by reference parity)
  • Per-head Q/K RMSNorm before rotary embedding
  • Attention width (4096) differs from hidden width (2560)
  • No BOS token; ChatML-style template pinned to Hugging Face's apply_chat_template
  • Tied output head: the artifact ships no classifier matrix; the embedding is reused, and NightRun's parity tests prove that against the reference

Granite 4.1 (conventional transformer)

  • GQA, SwiGLU, RMSNorm, tied embeddings, adjacent-pair RoPE (θ = 10M)
  • Four muP scalar multipliers (embedding, attention, residual, logits÷10) carried through the format and applied branch-free
  • The ÷10 logit scaling compresses top-2 gaps, making greedy near-ties measurably more common; a documented evaluation quirk, not a bug
  • Hybrid Granite variants (SSM/MoE) are intentionally rejected at conversion: supporting them would mean a different inference architecture, not a flag

10Tokenizer and chat-template correctness

A model that loads perfectly but tokenizes almost-correctly produces subtly broken output, the hardest kind of bug to see. NightRun treats tokenization as a correctness surface equal to the kernels:

  • byte-level BPE with each family's own pretokenizer regex;
  • fixture tests generated from the official Hugging Face tokenizers (with split_special_tokens; user text must never encode into control tokens);
  • chat templates pinned against apply_chat_template output token-for-token;
  • special-token round-trips and decode-encode identity tests.

11Correctness and validation

  1. GGUF inspection + metadata validation
  2. Kernel equality tests scalar vs AVX2 vs NEON, adversarial + saturated blocks
  3. Tokenizer + template fixtures vs Hugging Face reference
  4. Prefill bit-identity batched == sequential, logits and KV cache, per model
  5. Greedy generation parity token-for-token vs llama.cpp, all three families
  6. QEMU end-to-end scripted boots, screenshots, serial logs, x86 and AArch64
  7. Real hardware USB boot on x86; SD boot on a physical Pi 5
  8. Sealed-storage check post-load disk reads fault, proving true RAM residency

The parity rule is absolute: if a kernel or forward-pass change breaks token-for-token agreement with llama.cpp, the change is wrong, not the fixture. That rule caught a completely coherent-looking but subtly divergent Qwen implementation (the NEOX rope layout) before it ever shipped.

12Tradeoffs and the hard parts

Real systems have scars. A selection, told straight:

  • The soft-float trap. Rust's builtin x86_64 UEFI target is soft-float; AVX intrinsics don't even compile. NightRun ships a custom hard-float target JSON and builds core/alloc from source. (The AArch64 UEFI target, pleasantly, is hard-float out of the box.)
  • FP/SIMD isn't yours until you take it. x86 needs the XCR0 enable dance per core; on the Pi, the firmware launches applications with FP trapped: the first vector instruction dies silently. QEMU masked this; real hardware taught it.
  • Multicore has platform teeth. The ARM MP-services implementation refuses non-blocking startup after ready-to-boot; NightRun dispatches workers with a blocking call and a short timeout; PSCI can't preempt them, so "timeout" just means the workers keep running. The x86 path must keep the event-based variant, whose blocking mode would reset the workers instead.
  • The Pi boots nothing without device trees. Its bootloader refuses to start any UEFI payload unless matching DTBs sit next to it, discovered via the bootloader's own HDMI debug log during bring-up.
  • Someone has to spin the fan. On the Pi 5 the fan is OS-managed; with no OS it stays off. NightRun finds the RP1 over PCIe and drives the fan pin at 100%: when you can't regulate, overcool.
  • Fair benchmarks are work. Granite's logit scaling makes greedy near-ties flip between numerically-equivalent implementations; the repo documents the top-2-gap methodology used to distinguish real bugs from legitimate divergence.
  • The installer is deliberately paranoid. Whole-disk flashing earns a fingerprinted device identity, a two-stage confirmation with an exact typed device path, and default readback verification, because "dd to the wrong disk" is the classic self-inflicted wound of this genre.
